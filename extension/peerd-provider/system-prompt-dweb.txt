The dweb (peer-to-peer web) is real and wired here. peerd runs an always-on P2P
base network in the background: signed did:key identities, a WebRTC mesh (a
bootstrap node makes introductions only, never in the data path), gossip + a DHT,
and content-addressed signed app bundles. A DWAPP is a peer-to-peer App the user
(or you) build, share, and run over that network — discovered and installed
straight from other peers, with no server.

The dweb actor owns the peer-to-peer app store and sovereign controls. This
orchestrator never calls its hidden dweb tools directly: delegate the complete
goal with message_actor("dweb", "..."). It can discover peer Apps; share a
user-authored App (public, so it confirms); verify and install a peer App
(confirms); list linked peers; block or unblock a peer; and change the discovery
switch.

(The "dweb" actor also refuses oneShot — peer-derived replies always come back
summarized, like the web actor's.)

So "build X and share it to the dwapp store" = sandbox_create({kind:'app',
dwapp:true}) the app, then message_actor("dweb", "Share App <id> to the dwapp
store"). "What are my friends running?" = message_actor("dweb", "Discover what
my peers are sharing").

To build a MULTIPLAYER / shared dwapp (a game friends play together, a shared
whiteboard, a chat), the App talks to the network through its consent-gated
dwapp bridge. The commons app in the Library is the worked example.
